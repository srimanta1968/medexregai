MedexRegAI system architecture v2.0

The v1.0 architecture (a governed FDA knowledge base, retrieval-grounded AI with a citation gate, and multi-tenant workspaces) stays. v2.0 adds a second, separate pipeline for untrusted client documents, read-only connectors to the stores firms already use, a contradiction engine, drafting with citations to client pages, and Word as the review surface.

ExtendsMRA-PRD-008 Rev 1.0. Sections not mentioned here are unchanged.
ShapeModular monolith plus workers; one PostgreSQL with pgvector; S3; Claude API. A sandboxed document-conversion pool is the one new runtime.
New modulesintake, docproc, evidence, drafting, office
StatusADR-011 to ADR-018 proposed, for approval in Phase 0

1Architecture principles

  1. Provenance is structural (kept). Every fact carries its source. For client files that means file, version, hash and location (page, sheet and cell range, or slide), as well as the FDA record and snapshot.
  2. The model never recalls facts (kept). It reasons over retrieved passages and cites them. The citation gate now resolves client sources too.
  3. Client documents are untrusted input (new). They are parsed in a sandbox, passed to models only as data, and can never change system behaviour.
  4. Fit around existing systems (new). Read-only access to the firm's file store, Word out, PDF/DOCX records into any eQMS. No integration with the eQMS, accounting or CRM is required.
  5. Registers, not repositories (kept, made stricter). Linked files are fetched on demand, processed, and the fetched copy is discarded. We keep extracted text, locations, structure and hashes.
  6. Two pipelines, one model. The FDA corpus pipeline (public, shared, snapshotted) and the client-document pipeline (private, per tenant, deletable) never share storage or jobs. They meet only in retrieval, behind row-level security.
  7. Deterministic where possible. Value comparison, table matching, file-name and size checks are code, not prompts. Models handle reading, classification and prose.
  8. Boring, few moving parts (kept). One database, one object store, one queue. Split only on measured need.

9Citation gate v2

  1. Cite. Drafts cite FDA passages as [R:record#passage] and client sources as [C:file_version#location].
  2. Resolve. Every cited ID must exist, belong to this workspace (or the public corpus), and point at a current FileVersion, or at a superseded one with a warning.
  3. Match. The quoted span must match the extracted text at that location. Numbers, units, standard editions and dates in the sentence must equal an ExtractedFact at a cited location.
  4. Cover. Every sentence with a factual entity (number, standard, material, method, date, K-number) must carry a citation.
  5. Remove and log. Failing sentences are removed and listed as open items for the consultant. The gate cannot be turned off.

10Contradiction engine

  • Normalise facts by key: units (mm, in), durations (months, years), standard identifiers and editions (ISO 11135:2014 vs ISO 11135), sterilisation methods, material names (with a synonym list), model names.
  • Compare deterministically across all current versions for the same device: different values for one key make a candidate. Results are compared against acceptance criteria where both are present.
  • Use the model only for free text such as IFU wording against labelling or claims, and only with both passages shown.
  • Rank by section and severity (for example, shelf life in the IFU above what the ageing report supports ranks high). Repeat findings are suppressed. Resolutions are kept, so a resolved conflict does not return unless a new version changes it.
  • Evaluate on labelled packages: precision (≥ 70% judged real) is the gate metric, because false alarms cost consultant time.

11Word round trip

  • Export. Draft built on the firm's own template if one is set (FR-14.24), else ours. Each statement is wrapped in a bookmark carrying its statement ID. A Word comment on it lists the source file, version and page, with a link into the review screen. Open items appear as comments, not body text.
  • Re-import. The edited DOCX is matched by bookmark. Changed text becomes a ReviewEdit marked human-approved. New text without a bookmark is kept as human text. Deleted statements are recorded.
  • Fallback. If bookmarks are lost (copy-paste into another file), match by text similarity and ask the user to confirm.
  • No add-in in Release 1. A Word add-in follows only if peers ask for it (ADR-015).

12Key flows

12.1Connect and sort

User picks a folder → StorageConnection created with read-only scope → intake.list enumerates files → one docproc.process(version) job per file → classification and version jobs → evidence.compare(project) → sorted folder and problems ready. Target: 500 files in 60 minutes.

12.2A client sends a new revision

Webhook, delta feed or nightly hash finds a change → new FileVersion → pipeline steps 1–8 for that file → version chain updated (asks if unclear) → evidence.compare re-runs → revision impact lists every fact, finding, statement and table cell that cited the old version → the consultant chooses what to re-draft.

12.3Draft and review

Consultant requests a section → retrieve located passages and facts for the section → drafting route → citation gate v2 → thin FDA checks on cited predicates and standards → DOCX export → consultant edits in Word → re-import → ReviewEdits recorded → section marked reviewed → eQMS record export.

15Deployment and operations

  • Unchanged: AWS, one US region (ADR-001); containers on a managed service; Terraform; dev, staging and production, with the pilot as a production tenant.
  • New: a docproc worker pool in an isolated subnet with no internet egress, scaled on queue depth; an OCR pool if the chosen engine is self-hosted.
  • Observability: tracing across fetch → parse → classify → draft → gate, so a wrong statement can be traced to the stage that caused it. Per-project metrics: pages, unreadable files, AI cost, time to sorted folder.
  • SLOs: 99.5% monthly availability; 500 files sorted in 60 minutes; one section drafted in 10 minutes.
  • Runbooks: connector token revoked, provider outage, OCR backlog, injection alert, deletion request.

18Keeping the long-term path open, at little cost

The viability review sets out a long-term outlook: lab test data, suppliers and OEMs, customers, field operations, and patient data, each stage gated on the last. None of it is in scope. Three choices now keep it possible:

ChoiceWhat we do now
One device recordDevice has a stable identity with a nullable UDI-DI, so tests, suppliers, clearances and field data can link to it later.
Data rightsNo training on client data stays the default and a selling point. DataUseConsent exists from day one, off by default, never a condition of purchase.
Where data lives"Registers, not repositories" and no PHI hold for stages 1–4. Stages 5–6 would need customer-controlled stores and a separate PHI environment, so the boundaries stay clean.

Don't lead with this outlook in front of consultants. It adds to their worry about scale and could make us look like a future competitor.
