Client Evidence to Submission

MedexRegAI reads client files where they already sit, sorts them into eSTAR sections, finds what is missing or contradictory, and drafts sections in Word with every statement linked to its source page. The consultant reviews, decides and files, as they do today.

Primary buyerUS 510(k) regulatory consultancies, multi-client
Second buyerManufacturers' RA teams that file repeatedly (fallback (a) in the viability review)
New requirement groupFR-14.1 – FR-14.24 (FR-14.1–14.19 from addendum Rev 0.1; FR-14.20–14.24 new here)
Build gateGate V on 18 Dec 2026: problem size, solvability and willingness to pay (delivery plan §3)

1Purpose and outcome

A consultant connects one client project folder. Within an hour they see every file sorted by eSTAR section and version, a list of what is missing, and the places where the client's documents disagree with each other. A drafted request goes to the client, who uploads files through a link with no account. The consultant then gets Word drafts of the evidence-heavy sections and tables, with every statement traceable to a file, version and page, and FDA checks already run on the draft. They edit in Word, and the edits come back as human-approved text. They file the eSTAR themselves.

4Product principles

  1. Hours first, measured hours. Build in the order a consultant's measured hours are spent. When the measurement changes, the order changes.
  2. Fit around what firms run. We are not a system of record, a document control system or an eQMS. Files stay in Dropbox, Box, SharePoint or Drive. Records leave as PDF or DOCX.
  3. Registers, not repositories (kept from v1.0). We store links, hashes, extracted text with locations, statuses and relationships. Uploaded files are kept only when the user uploads instead of linking.
  4. Word is the review surface. The consultant's working document stays theirs. We add comments that link to sources and read their edits back.
  5. Every statement has a source. The citation gate now covers client files as well as FDA records: file, version and page, or the statement is removed.
  6. Never silently guess. Unclear versions, unreadable files and low-confidence values are shown and asked about, never decided quietly.
  7. The consultant decides, files and signs. We never file with FDA, never sign, and never message a client without the consultant's approval.
  8. Remove adoption cost before charging for it. Validation, data handling and onboarding material are part of the product, not add-ons.

6End-to-end workflow

Story. A consultant connects the client's Dropbox folder for a sterile single-use device. In 40 minutes the tool lists 212 files in 11 eSTAR sections, marks 3 superseded test reports, and flags that the IFU states a 3-year shelf life while the ageing report supports 2 years. It drafts a request for the missing EO residuals report, the consultant edits and approves it, and the client uploads the report through the link. Next day the consultant opens a Word draft of the sterilisation and shelf-life section. Each sentence carries a comment pointing to the report page, and the shelf-life conflict is listed as an open item. (Illustrative; figures are not measurements.)

11Screens and outputs

S1

Connect

Pick a folder in Dropbox, Box, SharePoint or Drive, or get the upload link and forwarding address. Shows scopes in plain words.

S2

Sorted folder

Files by eSTAR section and type, version chains, unreadable files, one-click corrections.

S3

Problems

Missing items and contradictions side by side with both source pages; resolve, accept with reason, or ask the client.

S4

Client request

Drafted request list, edited and approved by the consultant; status until received.

S5

Review

The single review screen: draft status per section, open items, revision impact, Word export and re-import.

S6

Records

Dated PDF/DOCX record, readiness package, validation and data-handling packs, usage export.

Outputs are Word section drafts with source comments, Excel summary tables, the readiness attachment list, admin documents with blank signature fields, and the eQMS record. eSTAR XML is added only if the spike works.

13Out of scope

  • Filing with FDA, CDRH Portal transmission, or signing anything.
  • Being a system of record: no check-in/out, e-signatures, Part 11 document control or training matrices.
  • Replacing the eQMS, document management, accounting, onboarding, sales or data-exchange tools.
  • Analysis of raw data and native CAD parsing (Ecosystem stage 2 at the earliest).
  • Writing clinical or expert judgement: the tool drafts from evidence and flags what needs judgement.
  • Messaging clients without the consultant's approval.
  • Using any client's data for another client or for model training. The future data-use opt-in has no effect in stage 1.

14Open questions (answered by Gate V or Phase 0)

  1. How much of the 60 hours is finding, chasing and reconciling, and how much is judgement? (Workbook A3.)
  2. Which two file stores do peers use most? That decides the first two connectors. (A2.)
  3. Do client agreements allow an outside AI service to process client files, and what would have to be true? (A4.)
  4. Who writes the technical sections: consultant or manufacturer? This sets the size of the complex-project saving. (A3.)
  5. Does generated eSTAR XML import cleanly into a blank nIVD v7.1 template? (Spike.)
  6. What happens to freed hours: more projects, less billing, or margin? (A5.)
  7. Have peers tried Complizen or Assyro for drafting, and what did they find? (Calls.)
